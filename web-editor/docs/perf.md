# 성능 측정

테스트: `tests/e2e/acceptance.spec.ts`의 A1(재생·드래그·트림)과 A2(60초 내보내기).
큰 파일은 저장소에 넣지 않고 만들어 쓴다.
```
npm run fixtures:perf                     # .perf-fixtures/clip1~5.mp4 (1080×1920 30fps 12초, 8Mbps)
PERF_DIR=$PWD/.perf-fixtures npx playwright test acceptance
```
자료: 1080×1920 H.264 12초 클립 5개를 메인 트랙에 이어 붙인 60초 프로젝트.

## 판단
- GPU가 없어 영상을 CPU로만 풀고 만드는 2코어 환경에서도 A1·A2 기준을 지켰다. 사용자 노트북은 하드웨어 디코딩·인코딩을 쓰므로 이보다 나쁠 이유는 적지만, **판정은 사용자 노트북(확인 2, 5번 항목)**에서 화면에 표시되는 시간으로 한다.
- **측정 주의:** 같은 2코어에서 A1·A2를 다른 테스트와 동시에 돌리면 29~54fps, 67.7초로 크게 나빠졌다. 측정끼리 CPU를 뺏기 때문이다. 그래서 CI는 A1·A2를 다른 테스트가 끝난 뒤 **단독으로** 돌린다. 2코어 러너는 "일반 노트북"이 아니므로 CI에서는 재생 수치(A1)를 기록만 하고, 드래그·트림 반응과 내보내기 결과물은 검사한다.
- 다음 클립으로 넘어갈 무렵 한 번 짧게 느려진다(8코어 58ms, 2코어 90ms, 약 2~3프레임). 원인은 아직 확인하지 않았다. 다음 클립 요소를 미리 만들어 불러오는 때로 추정한다. 사용자 확인 결과를 보고 태스크 10.6에서 다룬다.

확인 2의 5번 항목(60초 내보내기가 60초 안에)은 사용자가 통과로 판정했다. 숫자를 받으면 이 표를 채운다.

### 같은 조건으로 다시 잰 값 (A2, 효과 없음)
같은 기계에서 확인 2 빌드(`dfa7c60`)와 2-1 빌드를 **번갈아** 돌렸다. 기계 상태 변화가 한쪽에만 섞이지 않게 하려는 것이다. 자료와 절차는 위 A2와 같다.

| 환경 | 확인 2 빌드 | 2-1 빌드 | 차이 |
|------|------------|----------|------|
| 샌드박스 8코어 (GPU 없음) | 18.2 / 18.2 / 18.2초 | 18.4 / 18.4 / 18.3초 | +0.2초 (+1%) |
| 2코어 (`taskset`, CI와 같은 코어 수) | 33.1 / 33.0초 | 33.5 / 33.4초 | +0.4초 (+1%) |
| CI 러너 (실행마다 다른 기계) | 30.5초 | 30.1 / 30.4초 | 러너 편차 안 |

→ 효과를 쓰지 않으면 체감할 차이가 없다. 효과가 없으면 내보내기는 WebGL 처리기를 만들지도 않는다(`needsEffects`).

### WebGL 효과를 켠 내보내기 (2-1 빌드, 같은 60초 프로젝트)
| 조건 | 샌드박스 8코어 | 2코어 |
|------|---------------|-------|
| 효과 없음 (위 A2) | 18.4초 | 33.5초 |
| 필터: 5개 클립 모두 '영화처럼' + 선명도 50 | 112.2초 | 193.8초 |
| 배경: 클립 80% + 흐림 채우기 + '영화처럼' | 127.8초 | 190.2초 |

- **이 숫자는 사용자 노트북의 예상치가 아니다.** 샌드박스와 CI에는 GPU가 없어, Chrome이 WebGL을 CPU로 흉내 낸다(렌더러 `ANGLE (… SwiftShader driver)`). 1080×1920 필터 한 번의 단계별 시간(8코어 / 2코어):
  업로드(2D 복사 + 텍스처 올리기) 7.6 / 7.8ms · 셰이더(선명도·비네트 포함) 29.7 / 64.7ms · 셰이더(색만) 15.7 / 29.4ms · 결과 가져오기 1.1 / 1.1ms · **필터 1회 전체 50.7 / 87.7ms**. 효과 없이 2D로 그리면 0.6ms다.
  1800프레임 × 50.7ms ≈ 91초이고 18초 + 91초 ≈ 112초라 측정값과 맞는다. 늘어난 시간은 거의 다 CPU로 흉내 낸 셰이더 계산이다.
- 사용자 노트북 Chrome은 같은 셰이더를 GPU로 돌리므로 이 계산이 훨씬 가볍다. 효과를 켠 내보내기가 60초 안에 드는지는 **노트북에서 재야 판정할 수 있다**. 확인 2 때와 같은 프로젝트로 ① 그대로 ② 모든 클립에 '영화처럼'을 적용해 내보내고, 화면에 뜨는 두 시간을 위 표에 적는다.
- 예외: GPU가 막힌 PC에서는 Chrome이 WebGL을 CPU 흉내(SwiftShader)로 대신할 수 있다. 이 자동 대체는 폐지 예정이라 곧 WebGL 자체가 만들어지지 않게 된다([Chromium 문서](https://github.com/chromium/chromium/blob/main/docs/gpu/swiftshader.md)). 대체될 때는 위 표처럼 느려진다. 이런 PC를 알아보고 효과 탭과 내보내기 창에서 미리 알리는 일을 2-8에 넣었다.
- 재는 방법: `PERF_DIR=$PWD/.perf-fixtures npx playwright test acceptance -g "A2" --workers=1` (A2, A2-필터, A2-배경). CI는 효과 두 가지를 기본으로 건너뛴다. GPU가 없어 한 번에 몇 분씩 걸리기 때문이며, `A2_FX=1`이면 돈다.

## 원본 색 해석 차이 (2단계 2-1에서 발견·수정)
필터 미리보기=내보내기 테스트가 640×360 원본에서 3.8(기준 3)로 실패해 원인을 찾았다. 필터와 상관없이 **원본을 푸는 단계**에서 이미 달랐다.

| 원본 (색 정보 없음) | `<video>`(미리보기) | Mediabunny 기본(내보내기) | 두 길 차이 |
|--------------------|--------------------|--------------------------|-----------|
| 640×360, 360×640, 720×480, 960×540, 1280×718, 400×718 등 세로 < 720 | BT.601 | BT.709 | 평균 8.3~8.5 / 255 |
| 1280×720, 540×960, 720×1280, 1080×1920 등 세로 ≥ 720 | BT.709 | BT.709 | 0 |
| matrix만 적힌 SD | BT.601(적힌 값 무시) | BT.709 | 8.3 |
| 셋 다 적힌 원본(SD에 BT.709, HD에 BT.601 포함) | 적힌 값 | 적힌 값 | 0 |

- 판정 방법: 같은 프레임을 ffmpeg로 BT.601·BT.709를 강제해 풀어 두 브라우저 결과와 각각 비교(맞는 쪽 차이 0.7~0.9, 틀린 쪽 8.6~9.1). 규칙은 Chromium 소스(`media/ffmpeg/ffmpeg_common.cc`)와 같다.
- 수정: 내보내기·썸네일 디코더에 Chrome과 같은 색 공간을 넣는다(`src/media/color.ts`). 수정 뒤 20가지 모두 두 길 차이 0.00. 필터+흐림 배경 미리보기=내보내기 3.81/3.95/3.83 → 2.09/2.16/2.17.
- 확인 2까지는 비교 영상이 모두 540×960(규칙상 BT.709라 우연히 같음)이어서 드러나지 않았다. 휴대폰 촬영본은 보통 색 정보가 다 적혀 있어 영향이 없고, 색 정보 없는 옛 영상·일부 변환 파일에서 생긴다.
